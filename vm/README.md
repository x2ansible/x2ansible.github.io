# X2A development VM

A Fedora bootc VM running kind, community RHDH, PostgreSQL and X2A.
The application is deployed by the bundled Helm chart in `charts/x2a`.

There are two guest commands:

```bash
/opt/x2a/install.sh   # first installation only; not an update command
/opt/x2a/status.sh    # check services, workloads and HTTPS
```

Both run as root. The install service runs on boot, but the script is deliberately
create-only: an existing namespace, Secret or release causes failure. It does not
reconcile an existing VM on later boots. Existing workloads stay on the persistent disk.

## Build and run

Requires a Linux host with rootless Podman, Make, `bcvk`, libvirt, QEMU/KVM,
virtiofsd, `ip`, `jq` and access to `/dev/kvm`.
See [bcvk installation](https://github.com/bootc-dev/bcvk/blob/main/docs/src/installation.md).

1. Review [`cloud-init/user-data`](cloud-init/user-data). The supplied seed
   contains **dummy credentials**. Never serve real credentials through the HTTP seed.
2. Build the image:

   ```bash
   make build
   ```

3. Serve the seed in a separate terminal, then launch:

   ```bash
   make virt-serve
   ```

   ```bash
   make run
   make ssh
   ```

4. Inside the guest, check startup:

   ```bash
   /opt/x2a/status.sh
   ```

Open **https://localhost:8443**. The localhost certificate is self-signed and
valid for 30 days. Plugin downloads and application startup can take time;
HTTPS can return 502/503 until RHDH is ready.

Defaults: 4 CPUs, 16 GiB RAM, 60 GiB persistent disk, VM `kind-vm`.
`make stop` and `make start` preserve its data.
`make virt-destroy` permanently removes it.

`make run` does not rebuild the image or update an existing VM. Image changes
require a rebuild and a new VM. Cloud-init applies the seed on first boot only.

## Configuration

`cloud-init/user-data` writes configuration under `/etc/x2a/` on first boot.
The dummy values cannot authenticate to Bedrock, AAP or GitHub. Transfer real
credentials over an authenticated channel, not the HTTP seed.
Use literal `KEY=value` lines without shell quotes or expansion.

Keep `cloud-init/meta-data`: NoCloud fetches it alongside `user-data` for the
instance ID and hostname. Both `make run` and `make virt-serve` require it.

Cloud-init writes these files:

| File | Purpose |
|---|---|
| `llm.env` | LLM job parameters, as literal `KEY=value` entries |
| `aap.env` | `AAP_*` credentials; file required by the installer |
| `auth.env` | OAuth credentials; file required (may be empty) |

All three files must exist. The installer does not read `/etc/x2a/environment`;
set `global.x2a.publicUrl` in `charts/x2a/values.yaml`.

### Edit the chart

The source chart contains only:

```text
charts/x2a/Chart.yaml
charts/x2a/Chart.lock
charts/x2a/values.yaml
charts/x2a/templates/rbac.yaml
charts/x2a/templates/app_config.yaml
charts/x2a/templates/dynamic-plugins.yaml
```

- **App config:** edit the YAML under `data.app-config.x2a.yaml` in
  `templates/app_config.yaml`. Helm expressions work directly here.
- **Plugins:** edit `data.dynamic-plugins.yaml` in
  `templates/dynamic-plugins.yaml`. Helm expressions work here too.
- **RBAC:** edit `templates/rbac.yaml`.
- **Deployment settings:** edit `values.yaml` (image, database, mounts,
  public URL). Application configuration no longer lives in values.

Generate the full Kubernetes manifests, including RHDH and PostgreSQL:

```bash
make render
# output: render_helm.yaml
```

Requires Helm and network access to download the locked dependency (5.12.13).
Dependencies are built in a temporary copy; the source tree stays clean.
The image build bundles the same dependency for offline chart installation.

Offline rendering leaves `credentials.llm`, `auth.providers` and `signInPage`
null. There are no fallback LLM keys or guest-auth fallback.
To include **all key names from your actual LLM Secret**, or preview OAuth,
render against the cluster:

```bash
make render HELM_ARGS='--dry-run=server --kubeconfig /path/to/kubeconfig'
```

The rendered output includes dependency-generated Secrets. Treat
`render_helm.yaml` as sensitive; do not publish live-cluster renders.
Passwords generated by the dependency may differ between renders.

### First installation and credentials

The VM installer creates namespace `rhdh`, then creates `x2a-llm`, `x2a-aap`
and `x2a-auth` with three explicit `kubectl create secret --from-env-file` commands.
It then runs `helm install rhdh /usr/share/x2a/chart --namespace rhdh`.
No updates, existence checks, dummy fallbacks, Helm overrides or rollout restarts.
The script stops on errors, including missing env files and existing resources.
Use a fresh VM for this create-only installation.
All LLM Secret keys are forwarded as `${KEY}` references to conversion jobs;
there is no provider-specific key list. Use only trusted uppercase environment
names, and keep AAP/OAuth keys out of the LLM Secret.

Authentication reads `x2a-auth` directly. Each `AUTH_GITHUB_CLIENT_ID`,
`AUTH_GITLAB_CLIENT_ID` or `AUTH_BITBUCKET_CLIENT_ID` key enables that provider
and adds it to `signInPage`. Supply the corresponding `*_CLIENT_SECRET` too;
the template deliberately does not validate pairs or values. Missing or
unrecognized Secrets produce null providers and a null sign-in page.
The six known OAuth variables are imported through optional Secret references.

```bash
kubectl -n rhdh create secret generic x2a-auth --from-env-file=/path/to/auth.env
make render HELM_ARGS='--dry-run=server'
```

There is no `oauthEnabled` flag. The old `rhdh-oauth` Secret is no longer read.
GitHub/GitLab resolve by username; Bitbucket uses the username annotation.
The development resolvers allow users without catalog entries; keep the VM private.

**Reset compatibility:** combined `credentials.env`, legacy
`x2a-credentials` migration, `auth-values.yaml` and
`global.x2a.appConfig` overlays are no longer supported. Split credentials into
the env files above; put custom auth configuration directly in the template.
This is a chart reset, not an automatic migration of old Helm releases.
Prefer a fresh development VM; old Helm-owned Secrets may require manual
migration before upgrading.

Updates and credential rotation are manual operations outside this installer.
Do not rerun it to update a release or restart workloads.

Credential files are no longer staged inside the chart or stored in Helm
history by the installer. Helm still retains rendered app config and
dependency-managed Secrets. Historical releases from before this reset may
contain staged credentials. Never bake real credential files into the image
or transfer them through the HTTP seed.

The public URL comes from `global.x2a.publicUrl` in `charts/x2a/values.yaml`.
For another port, edit that setting before building, for example
`https://localhost:9443`, then use:

```bash
make build
make run HTTPS_PORT=9443
```

The seed's old `PUBLIC_URL` setting is not used by the installer.
Do not change host firewall or privileged-port policy automatically.

## Troubleshooting

Inside the guest:

```bash
/opt/x2a/status.sh
journalctl -u kind -u rhdh -u x2a-port-forward -u x2a-https -f
```

The HTTPS path is guest nginx → loopback kubectl port-forward → RHDH.
The port-forward retries on pod replacement. SELinux remains enabled where
supported; the proxy unit enables its network-connect boolean. Existing TLS
files are never overwritten; replace both certificate and key before
restarting `x2a-https`.

**Development only:** broad job/Secret permissions, mutable application/plugin
tags and development authentication are enabled. Do not expose this VM publicly
or deploy it on a shared cluster. Host forwarding may bind all interfaces.
A passing status check does not verify an end-to-end conversion. Persistent
disk expansion is unverified; if `/var` is tmpfs, its limit shares guest RAM.

## Checks without building a VM

```bash
python3 -m unittest discover -s tests
helm lint charts/x2a
make -n build run ssh stop
```

Tests cover offline rendering, live Secret key discovery, OAuth selection and
ConfigMap mounts using a mock Kubernetes API. These checks are not a VM boot test.
